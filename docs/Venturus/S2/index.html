Atrium: managing a campus's AV estate.

A web tool the central IT team of a university uses to manage the audio-visual and room-control infrastructure of every lecture hall, lab and library: projectors, microphones, door readers and room panels. Three working prototypes of its core flows, fully clickable with sample data, each backed by requirements, error cases, open questions and a change history.

In short

The insight: Atrium writes to an external system of record that can refuse a change, so refusal is designed as a first-class state. Blocked actions stay visible and explain themselves in a toast or tooltip.

What you can open: three clickable prototypes (infrastructure, devices, device recovery), each backed by requirements, error cases and a knowledge base. I designed them working with stakeholders and users of an international client.

How AI was used: only on this project, to prototype, document and organise it. Every other project on this site is handcrafted.

Prototypes

Each prototype covers one of the three jobs people do in Atrium: see and change the infrastructure, register and retire devices, and recover devices that broke.

Manage Infrastructure

For Campus IT Admins

One place to see and change the infrastructure: a tree of Campus → Building Controllers beside a context-aware details panel, a Manage menu and a unified Create Node drawer. The design problem: configuration cascades from the campus down, and admins must always see where a value comes from and why a change is blocked.

Open prototype →

Manage Devices

For AV Technicians, Faculty Coordinators and Campus IT Admins

A table of the devices themselves, switching between IT-managed and Faculty-registered views of one dataset, with an Add devices wizard and a status model (Active, Ready, Retired). The design problem: two device types share most screens but differ in who registers them and where their data comes from.

Open prototype →

Device Recovery

For Campus IT Admins

Makes recovery registration visible per device, adds a safety valve to force a new registration, and a Roll out tab to push a recovery version. The design problem: status must be trustworthy at a glance, and manual overrides must be clear without inviting misuse.

Open prototype →

How the pieces fit

Edge and hub

Each building has a Building Controller (an edge server) that talks to its devices and pulls timetables and room policies from a Campus Hub; a Timetable Relay mirrors files out to the controllers.

Refusal is a design concern

Most of what Atrium writes lands in an external system of record (the Asset Registry), which can refuse a change, so nearly every blocked action explains itself in a toast or a tooltip.

Roles and views

A navbar toggle switches the app between IT-managed and Faculty-registered devices, and two personas, a Campus IT Admin and a Viewer, show how permissions change the interface.

Design process

Atrium was designed the way I work on client products: start from what people and systems actually need, write it down so it can be challenged, prototype it until the edges show, and leave a trail the engineers can build from. The artefacts below are all inside this folder.

  1. Understand

    Discovery sessions with stakeholders, recorded and transcribed, plus the systems Atrium has to sit between (Campus Hub, Asset Registry, Room Booking Manager…).

    Transcript-4.vttsystem-overview.md

  2. Define

    Versioned requirements with traceable IDs (FR-…, UX-…), a shared glossary, and the roles and permission gates.

    requirements.mdglossary.mdroles-permissions.md

  3. Prototype

    Clickable, in-memory prototypes on a shared design system and plugin components, built per feature so each can be changed safely.

    manage-infrastructure/manage-devices/device-recovery/

  4. Stress the edges

    Hidden error and blocked states, switchable demo states (?state=fsm-down), open questions, and heuristic review findings.

    error-cases.mdqa.mdfindings.json

  5. Hand off

    A router doc per prototype, a dated changelog, and a knowledge base that merges every source into one document per topic.

    PROTOTYPE.mdchangelog.jsonmodule-knowledge-base/

UI flow

How every screen connects, taken from the knowledge base. First the system map, then the paths inside each prototype. Every box is a real surface in the prototypes.

  • 1Device Recovery → Manage Devices: the row action See in Manage Devices opens it in a new tab, with campus, type and asset tag pre-filled.
  • 2Manage Devices → Device Recovery: the page already accepts a deep link (?station=&unit=), but no UI entry point calls it yet.
  • The Registered / Managed toggle resets the view in Manage Devices and is pinned to Managed in Device Recovery. Manage Infrastructure ignores it.
  • Roles hide whole menu items: the Viewer persona never sees Manage Infrastructure.

Design patterns

Patterns that recur across the three prototypes. Spotting them early is what let one module reuse another's decisions, and what keeps the product feeling like one tool.

Interaction patterns

Flow

Select, review, commit

Gather a selection, show what will change, then commit and report successes and conflicts separately. A conflict keeps the flow open on what still needs attention.

Used in Add Devices wizard · Send Recovery Request · Roll out · bulk Registry Sync

Feedback

Blocked actions stay visible

An action that is not allowed is still listed, but inert, with its reason in a tooltip. People learn why instead of wondering where the action went.

Used in Archive and Move gates · Send Recovery Request · Retire

Feedback

Partial success is a result

When a bulk action succeeds on some items and is refused on others, the toast says which, rather than collapsing into pass or fail.

Used in Registry Sync cascade · Add Devices · Send Recovery Request

Safety

Unsaved-change guards

Panels hold Save and Discard until a field differs from its snapshot. Closing a drawer or wizard with pending input asks to keep editing or discard.

Used in Details panel · Create Node drawer · Add Devices wizard

Safety

Reversible removal

Nothing is permanently deleted. Archived items are hidden by default, revealed by a toggle, and can be restored to their origin.

Used in Archive / Unarchive · Retire

Structure

Master–detail

Pick something in a list or tree and edit it in a side panel. Creation and removal live in a separate Manage menu so the panel stays about one thing.

Used in Tree + details panel · Roll-out history dialog

Structure

One surface, several modes

A single drawer serves Create, Unarchive and Move, adapting its title, fields and defaults to where it was opened from.

Used in Create Node drawer

Structure

Stepped wizard

Long, error-prone tasks are broken into named steps whose state follows the data, with a shared footer and clear exit.

Used in Add Devices · Roll out · Import version

Navigation

Scope in the sub-header

Campus and faculty pickers sit in the sub-header and filter everything below. Dependent controls stay hidden until a scope exists, and empty states say what to pick.

Used in All three prototypes

Data

Counter cards as filters

Summary numbers double as toggle buttons: a count is also the shortcut to the rows behind it.

Used in Device Recovery registration

Data

Grouped, sortable table

Collapsible group rows, header sort that cycles asc/desc/off, column filters with a visible Clear Filters, and muted rows for ineligible items.

Used in Manage Devices · Device Recovery

Feedback

Inline field errors

Every validation message comes from one component and one shape: “Enter <Label>”, “Enter a valid <Label>”, “<Label> already in use”.

Used in Create Node · Add Devices · Import

Construction patterns

Architecture

Shell + page content

Each prototype is a static page inside a shared Canvas shell. Navigation and sub-headers come from one JSON file, so the three modules behave as one app.

Where runtime/canvas-navigation-data.json

Architecture

Feature modules

Plain JavaScript and CSS split per feature (tree rendering, bulk mode, search, wizard…), each with a short map of what it does and depends on.

Where js/ · css/ · maps/

Components

Design system + project plugins

A tokenised design system supplies the basics. Project plugins add what it lacks (cascader, multi-select, wizard, timeline, source toggle) and are reused across modules.

Where runtime/plugins/

Testability

Demo states

Failure and edge cases are switchable by query string (service down, partial failure, read-only), so each can be demonstrated and reviewed on demand.

Where ?state=fsm-down · partial · readonly

Access

Persona-driven permissions

A persona switcher stands in for sign-in. Roles hide, disable or lock elements by selector, so permission behaviour is visible without a backend.

Where runtime/davinci-users.json

Documentation

Docs inside the product

Requirements, error cases, open questions, changelog and the knowledge base open from the ribbon of the prototype itself, so reviewers never leave the context.

Where proj-requirements-panel · proj-kb-launcher
